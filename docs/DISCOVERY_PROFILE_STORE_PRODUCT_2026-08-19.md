# Discovery — الملف الشخصي والمتجر والمنتج

## نطاق الفحص

تمت مراجعة شاشة الحساب و`BecomeMerchantScreen` و`MerchantDashboard` وعقود Dart وشاشات `ProductDetailScreen` و`StoreProfileScreen` وواجهات Repository ومخطط migrations ذات الصلة. لم تُجرَ أي تغييرات على كود الإنتاج أثناء مرحلة Discovery.

## النتيجة التنفيذية

الواجهة الحالية تملك أساسًا صالحًا لإعادة الاستخدام، لكنها لا تطبق بعد تجربة المتجر الفورية والتحكم الكامل التي اعتمدها المستخدم. أهم فجوة ليست في الشكل فقط، بل في **نموذج الحالة**: الشاشة الحالية تفصل بين طلب التاجر والمتجر، وتمنع إدارة المنتجات قبل التفعيل، بينما المطلوب أن تُفتح مساحة متجر قابلة للتحرير فورًا وتبقى حالة النشر معلقة حتى موافقة الإدارة.

| المسار | الموجود فعليًا | الفجوة المؤكدة | مستوى الخطر |
|---|---|---|---|
| الملف الشخصي | اسم وصورة حرفية وبريد وإحصاءات وأزرار الطلبات وكن تاجرًا | لا يوجد غلاف/ملف غني/تحرير عام/موقع جغرافي فعلي/عرض متجر متكامل | عالٍ |
| إنشاء المتجر | شاشة واحدة طويلة، حفظ مسودة، رفع شعار وغلاف، إرسال طلب | لا يوجد Wizard تدريجي، ولا مساحة متجر فورية، ولا معرض صور متعدد، ولا إدخال تخصصات مرجعي متعدد | عالٍ |
| لوحة التاجر | تعرض حالة الطلب وبطاقة منتجات نصية فقط | تمنع إدارة المنتجات قبل التفعيل، ولا توجد تبويبات أو إحصاءات أو تعليقات أو ردود أو طلبات أو محرر | حرج |
| المتجر للعميل | صفحة قراءة طويلة فيها غلاف رمزي، معلومات، صور إن وجدت، متابعة ومراسلة ومنتجات | لا توجد Pager/تبويبات ثابتة للمنتجات والمعلومات والتواصل، وتختفي صور المتجر إذا كانت القائمة فارغة | متوسط/عالٍ |
| المنتج للعميل | معرض وصورة وبيانات وإعجاب ومفضلة وطلب وتقييمات وتعليقات في Scroll واحد | لا توجد تبويبات معلومات/تفاعل/مشابهة، ولا محرر تاجر قابل لإعادة الاستخدام | عالٍ |
| كتابة المنتجات من Flutter | العقد يحتوي قراءة المنتجات وتفاعلها، لكن `AssalRepository` لا يقدم Create/Update Product للتاجر | لا يمكن للتاجر تنفيذ الرفع المطلوب من تطبيق العميل دون عقد Repository وGateway وRLS | حرج |
| تعديل البيانات | لا يوجد مسار عام لتعديل ملف أو متجر أو منتج بعد النشر | لا يوجد versioning أو `pending_update` أو سياسة نشر للتعديلات الحساسة | حرج |
| الإحصاءات | المنتج لديه `viewsCount` و`likesCount`، والمتجر لديه متابعون ومراجعات | لا توجد واجهة تاجر تعرضها، ولا تعريف موحد لتجميعها | عالٍ |
| التفاعل | العميل يستطيع إضافة مراجعة وتعليق؛ نموذج المراجعة يحتوي `merchantReply` | لا يوجد مسار واضح للتاجر لقراءة/الرد على التعليقات والمراجعات | عالٍ |

## الأدلة المصدرية المهمة

### شاشة التاجر الحالية

`apps/mobile_flutter/lib/features/merchant/merchant_dashboard.dart` تعرض حالة `merchant_applications` فقط. عند حالة غير مفعلة تقول إن إدارة المنتجات غير متاحة، وهذا يخالف القرار الجديد. لا يوجد فيها `TabBar` أو `TabBarView` أو Repository operation لإضافة منتج أو تعديله أو قراءة إحصاءات التاجر.

### شاشة كن تاجرًا الحالية

`BecomeMerchantScreen` في `customer_account.dart` تستخدم controllers نصية لـ`displayName`, `phone`, `experience`, `location`, `specialties`, `certificateNote`, و`storeDescription`. التخصصات والموقع نصوص حرة، وليسا معرفات من المرجع. الصور الحالية هي `logoUrl` و`coverUrl` فقط. الحفظ يكتب مسودة، والإرسال ينشئ طلبًا، لكن لا يُفتح متجر قابل للتحرير فور إنشاء المسودة.

النص الحالي يقرر صراحة أن المنتجات والصور تبقى مخفية حتى تفعيل المتجر، وهو مناسب للنشر العام لكنه يمنع تجربة التاجر المطلوبة. سيُستبدل لاحقًا بمنطق يفصل بين **إمكانية التعديل والمعاينة للتاجر** وبين **النشر للعميل**.

### عقود البيانات الحالية

`AssalStoreSummary` غني نسبيًا ويحتوي الغلاف والشعار والمعرض والتواصل والتوصيل والموقع والتخصصات والشهادات والإحصاءات. هذا يسمح بإعادة استخدام نموذج العرض، مع ضرورة توفير Store Editor وGallery write contract.

`AssalProductSummary` يحتوي معظم بيانات العرض المطلوبة، بما في ذلك الصور والخصائص والمصدر والتصنيف والمشاهدات والإعجابات والتقييمات. لكنه كيان قراءة؛ لا يوجد في `AssalRepository` عقد تاجر لكتابة منتج أو تحديثه أو حفظ نسخة معلقة.

`AssalUserProfile` يحتوي `avatarUrl` و`bio` و`phone` و`location`، لكنه لا يحتوي `coverUrl` أو عقد تحديث ملف مستخدم. إضافة غلاف الملف الشخصي ستحتاج تدقيق schema وStorage قبل تنفيذها.

`AssalMerchantApplicationDraft` يحتوي `regionId`, `logoUrl`, و`coverUrl` في العقد، لكن الشاشة الحالية لا تستخدم `regionId` فعليًا ولا تقدم معرضًا متعدد الصور أو بيانات متجر مستقلة.

### شاشات عرض العميل الحالية

`StoreProfileScreen` في `customer_catalog.dart` يستخدم Scroll واحدًا، ويعرض غلافًا gradient رمزيًا بدل `store.coverUrl`، ويعرض معرض الصور فقط إذا كانت القائمة غير فارغة، ثم المعلومات والتواصل والمنتجات. هذا يعني أن البنية قابلة لإعادة التنظيم إلى تبويبات، لكن يجب عدم حذف مسار القراءة الحالي أثناء النقل.

`ProductDetailScreen` يستخدم Scroll واحدًا طويلًا يعرض المعرض والملخص والبيانات والمتجر والإعجاب والمفضلة والطلب والتقييمات والتعليقات. لا توجد تبويبات للمنتج ولا قسم منتجات مشابهة. المكون الحالي مناسب ليصبح محتوى تبويب أو يُستخرج إلى مكونات مشتركة بين العميل ووضع المعاينة للتاجر.

## مخطط Production الذي يجب احترامه

المهاجرات الحالية تحتوي جداول `profiles`, `stores`, `store_gallery`, `store_statistics`, `products`, `product_images`, `reviews`, `comments`, `requests`, ومرجعيات التفاعل. توجد كذلك `product_view_events` و`product_likes` و`merchant_applications` و`merchant_application_drafts`. Migration 0016 تضيف حقول المتجر الأساسية وتربط قرار الإدارة بالدور والمتجر والإشعار.

لكن Migration 0012 تُظهر أن طلب التاجر الحالي يحفظ `specialties` و`location` كنصين، بينما التجربة المطلوبة تحتاج تخصصات متعددة بمعرفات مستقرة وموقعًا منظمًا. كما أن المخطط الحالي لا يثبت من هذه القراءة وجود versioning للمنتجات أو `pending_update` أو سجل تعديلات كامل؛ لذلك لا يجوز بدء تعديل المنتج بعد النشر قبل تدقيق الجدول والسياسات وإضافة تصميم إصدار آمن.

## مصفوفة العقود المطلوبة قبل التنفيذ

| الوظيفة | عقد واجهة مطلوب | Repository/Backend مطلوب | DB/Storage/RLS مطلوب |
|---|---|---|---|
| تعديل ملف المستخدم | profile editor + cover/avatar/location | get/update profile + upload profile media | حقول غلاف، Storage path، سياسة المالك |
| فتح المتجر الفوري | merchant workspace + pending banner | ensure workspace/draft + load state | فصل workspace عن published store |
| بيانات المرجع | multi-select taxonomy/region picker | list reference + save IDs | taxonomy/region IDs وسياسات القراءة |
| إضافة منتج | product editor/preview | create product draft | product owner policy وdraft status |
| تعديل منتج منشور | editor + diff/version badge | update or create pending revision | version/revision table أو fields، RLS، audit |
| صور المنتج | gallery picker/reorder/delete | upload/delete/reorder media | product_images ownership/storage policy |
| إحصاءات التاجر | dashboard cards/charts | merchant analytics query | views/events/likes query policy |
| تعليقات وردود | moderation/reply tab | merchant list/reply operations | author/merchant policy وaudit |
| طلبات وتواصل | merchant inbox | list/update request + messages | participant/merchant access policy |
| نشر بعد التفعيل | status banner + notification | atomic activation + refresh | existing RPC extended safely |

## بوابات عدم الكسر

لن يُعدّل `MerchantDashboard` أو `StoreProfileScreen` مباشرة بإعادة كتابة واسعة. سيتم أولًا استخراج مكونات مشتركة صغيرة، وإضافة عقود اختبارية، ثم ربطها بالتنقل الحالي. سيبقى مسار العميل القديم قابلًا للرجوع حتى ينجح المسار الجديد في الاختبارات.

لن يُسمح للتاجر برؤية المنتج للعامة قبل أن تكون حالة المتجر والمنتج مؤهلة للنشر. في المقابل، يستطيع التاجر إنشاء المسودة وتعديلها ومعاينتها فورًا. عند التفعيل ستُراجع العناصر المؤهلة وتُنشر ذريًا أو عبر Job واضح مع إشعار، مع بقاء العناصر غير المكتملة معلقة بدل فقدانها.

التعديلات بعد النشر ستحتاج تصنيفًا: تعديل فوري آمن أو `pending_update` للمراجعة أو إجراء إداري محمي. لا يجوز الكتابة فوق النسخة المنشورة بلا سجل أو جعل تعديل حساس يظهر مباشرة بلا تحقق.

## الخطوات التنفيذية التالية

1. تثبيت baseline فعلي على Windows للـFlutter وAdmin، وحفظ نتائج التحليل والاختبارات قبل تعديل UI.
2. فحص schema وRLS الفعليين في Production للجداول المذكورة، خصوصًا ownership للمنتجات والصور وحقول profile والغلاف.
3. إعداد عقد صغير للـmerchant workspace وproduct draft قبل بناء الواجهات.
4. إعادة استخدام مكونات Store/Profile/Product الحالية داخل تبويبات وواجهات تحرير، دون إنشاء تطبيق أو شاشة بديلة.
5. تنفيذ الحفظ والرفع والإحصاءات والتفاعل خطوة خطوة، مع اختبارات بعد كل خطوة.
6. اختبار التاجر قبل التفعيل وبعده، واختبار عميل مستقل للتأكد من أن المعلق لا يظهر للعامة.
7. تشغيل analyzer/tests/build، مراجعة diff، ثم تقرير قبول يوضح كل وظيفة ومسارها.

هذه الوثيقة هي نتيجة Discovery الأولية، وليست موافقة على Migration جديدة. أي تغيير مخطط قاعدة بيانات سيُفصل في ملف Migration مستقل بعد إثبات عدم توفر الحقول أو المسارات الحالية.

## Baseline Gate — Windows

قبل أي تعديل جديد، نجحت بوابة baseline على المصدر الفعلي في Windows: `flutter analyze --no-pub` بلا مشاكل، و`flutter test --no-pub` مع 13 اختبارًا ناجحًا، و`pnpm check` للوحة الإدارة، و`pnpm test` مع 4 اختبارات ناجحة. ستُستخدم هذه النتائج كمرجع عدم كسر، ولن يُقبل أي تغيير لاحق إذا لم يحافظ عليها.

## Production schema evidence

المشروع الفعلي هو `gvalqfgxrkibuydoiuiz` وحالته `ACTIVE_HEALTHY`. نتيجة `list_tables(verbose=true)` أكدت أن `profiles` لا يحتوي حاليًا على `cover_url`، وأن `merchant_profiles` يحتوي بيانات العمل وحالة التحقق، وأن `stores` يحتوي `region_id`, `name_ar`, `slug`, `description`, `phone`, `logo_url`, `cover_url`, `status`, و`is_verified`. يوجد `store_gallery` مستقل مع `media_url` و`sort_order`، و`store_statistics` مع المتابعين وعدد المنتجات والتقييمات.

أكد المخطط أن `products` جدول قراءة/بيانات أساسية يحتوي `store_id`, `taxonomy_id`, الاسم والوصف والنوع والجودة والحالة، و`product_images` جدول مستقل للصور والترتيب. توجد `reviews` و`comments` و`product_view_events` و`product_likes` لمسارات التفاعل والإحصاءات. طلبات التاجر موجودة في `merchant_applications` مع `store_description`, `region_id`, `logo_url`, و`cover_url`، لكن لا يوجد في الجداول الحالية إصدار منتج أو `pending_update` أو سجل تعديلات للمنتج حسب هذه القراءة.

هذه النتيجة تؤكد أن فتح مساحة التاجر فورًا ممكن معماريًا عبر مسودة/مساحة عمل، لكن **إضافة المنتج والتعديل بعد النشر لا يجوز تنفيذهما كـUPDATE مباشر من Flutter** قبل إضافة عقد كتابة وRLS ونسخ/حالة مراجعة مناسبة. كما أن غلاف ملف المستخدم يحتاج Migration منفصلة لأن `profiles.cover_url` غير موجود، ولا ينبغي إعادة استخدام `stores.cover_url` لهذا الغرض.
