# Phase 9 — خطة فحوص التكامل والأمان والأداء

## الغاية

تثبت هذه المرحلة أن منظومة **Souq Al Assal** تعمل وفق حدود Demo-First بعد اكتمال تطبيق الجوال في المصدر ولوحة الإدارة وصفحة الهبوط. لا تضيف المرحلة مصادر إنتاج أو حسابات أو بيانات جديدة؛ بل تتحقق من أن عقود Demo وواجهاتها ومسارات التشغيل وآليات الحماية لا تتعارض مع ثوابت المنتج.

## معايير القبول

| المجال | معيار القبول | الدليل المطلوب |
|---|---|---|
| سلامة Demo Catalog | عدد المنتجات والمتاجر والمناطق مطابق للمصدر، ولا تقييمات أو مراجعات مصطنعة | تشغيل `check_demo_catalog.py` وفحص JSON |
| تطبيق Flutter | يمر التحليل والاختبارات المتاحة دون اشتراط SDK غير موجود في البيئة | نتائج فحوص المصدر وذكر قيد Flutter CLI بشفافية |
| مشاريع TypeScript | تمر `pnpm check` و`pnpm build` للوحة/الصفحة | مخرجات البناء وتتبّع الأخطاء |
| فصل الإنتاج | لا تستدعي واجهات Demo Supabase، ولا تحتوي UI على مفاتيح أو أسرار | مسح ثابت للمصدر وملفات البيئة العامة |
| RLS والمخطط | تظل migrations الست صحيحة من ناحية البناء والحماية الساكنة | فحص migrations وسياسة RLS المنشورة |
| الأداء | لا توجد أصول محلية كبيرة داخل web project؛ تؤخذ الصور من التخزين المخصص | تدقيق مسارات الأصول وحجم build |
| عدم وجود واجهة ميتة | الأزرار تؤدي إلى انتقال أو Toast Demo صريح أو تكون معطلة بسبب مفهوم | مراجعة تفاعلية لمسارات الويب |
| المظهر | يتوافق RTL والهوية والخط والتباين مع Design System على desktop/mobile | لقطات تمثيلية وفحص يدوي |

## حدود المرحلة

لا يمثل اجتياز Phase 9 إطلاقًا عامًا، ولا إذنًا بنشر لوحة الإدارة، ولا انتقالًا من Demo إلى الإنتاج. ولا يجوز تفسير نجاح مخطط Supabase أو RLS على أنه دليل اكتمال Feature من دون تحقق الواجهة والحالة والعقد والتنفيذ التجريبي والأدلة.

## المخرجات

ينتج عن المرحلة تقرير Evidence موحد، وأي إصلاحات لازمة، وcommit GitHub. تحفظ نسخة checkpoint لمشروع الويب بعد اكتمال الفحوص، بينما يتطلب النشر العلني لصفحة الهبوط تفويضًا صريحًا مستقلًا من المستخدم.
