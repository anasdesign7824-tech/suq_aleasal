# سوق العسل اليمني — Product Vision

## تعريف المنتج

**سوق العسل اليمني (Souq Al Assal)** منصة عربية أولًا وRTL أولًا لاكتشاف العسل اليمني والتعرّف إلى مصادره وجودته والنحالين والتجار الموثوقين، ثم بناء علاقة تواصل واجتماعية وتجارية حول المنتج. المنصة ليست متجر Checkout تقليديًا؛ مركز الثقل فيها هو **الاكتشاف والثقة والتوثيق والتواصل والطلبات**.

> التجربة المستهدفة: «المكان المتخصص الذي أستطيع من خلاله اكتشاف العسل اليمني، معرفة مصدره وجودته، اكتشاف النحالين والتجار الموثوقين، متابعة متاجرهم، التفاعل معهم، السؤال والتواصل معهم، إرسال الطلبات، ومتابعة العلاقة معهم.»

## مبادئ غير قابلة للتفاوض

| المبدأ | القرار التنفيذي |
|---|---|
| Arabic First / RTL First | تبنى الواجهة بالعربية وRTL من البداية، لا كتوطين لاحق. |
| Discovery First | Home والبحث والتصنيفات والمنتجات والمتاجر هي محاور العميل. |
| Social Commerce | المتابعة والإعجاب والتقييم والتعليق والمراسلة جزء من النموذج الأساسي. |
| Request not Checkout | الطلب هو طلب تواصل/استفسار/شراء موجه للتاجر، وليس سلة ودفعًا تقليديًا. |
| Demo First | تعمل تجربة العميل كاملة دون إنترنت أو Supabase عبر عقود ومصادر Demo. |
| Backend Ready | لا يتصل UI بقاعدة البيانات؛ التبديل إلى Production يتم خلف Repository/Data Source. |
| Asset Fidelity | الخطوط وSVG والأيقونات والصور والتصنيفات الموجودة في المشروع تخضع للجرد وإعادة الاستخدام، لا للاستبدال العشوائي. |
| No Dead Controls | كل زر ظاهر ينفذ وظيفة أو يوضح سبب تعطيله أو لا يظهر. |
| Evidence Before GO | analyzer/build وحدهما لا يكفيان؛ القبول يعتمد على الرحلات والاختبارات والتدقيق البصري والبيانات. |

## الأطراف والقدرات

| الطرف | النطاق الكامل في المنتج | ما يدخل حزمة Customer Web/APK الحالية |
|---|---|---|
| Customer / Guest | اكتشاف، بحث، تصفية، تفاصيل، متاجر، متابعة، حفظ، تقييم، تعليق، طلب، رسائل، إشعارات، ملف شخصي، تحويل إلى تاجر | كامل مسار العميل في Demo، وتجهيز العقد للإنتاج |
| Merchant | إنشاء ملف تاجر، متجر، منتجات، توثيق، توصيل/استلام، Dashboard، طلبات، رسائل | المسارات العامة للمتجر والتحويل إلى تاجر وDemo creation حيث يلزم لإثبات رحلة العميل |
| Admin | إدارة المستخدمين والتجار والمنتجات والتصنيفات والبنرات والتوثيق والتقارير وRLS | خارج الحزمة الحالية؛ لا نبني Admin شكليًا داخلها |
| Public visitor | مشاهدة واكتشاف دون Login Wall | مدعوم من أول تشغيل |

## رحلة العميل المعتمدة

تبدأ الرحلة من تشغيل التطبيق ثم Home، ومنه إلى التصنيفات والبحث والفلاتر، ثم فتح المنتج والمتجر، متابعة المتجر، حفظ المنتج، التقييم والتعليق، إرسال طلب التواصل، مراجعة الملخص والإرسال، عرض الطلبات، فتح التفاصيل، المراسلة، ثم handoff عبر وسائل التواصل المناسبة. كل هذه الخطوات يجب أن تعمل في Demo Mode وأن تشترك Web وAPK في نفس عقود البيانات والمنطق.

## نطاق النسختين

تستخدم **Flutter Web** و**Flutter Android APK** قاعدة كود واحدة، مع responsive layout بدل تمديد واجهة الهاتف حرفيًا على سطح المكتب. يشترك الطرفان في Design System والعقود وUse Cases وRepositories وDemo/Production configuration. يختلفان فقط في نقاط المنصة مثل إدارة Share Sheet والكيبورد والـ viewport وأدوات Android.

## ما لا يدخل هذه الحزمة

لا تشمل هذه الحزمة تدقيقًا جنائيًا أو إعادة بناء مستقلة لـ **Admin Web** أو **Supabase schema/RLS** أو **Landing/Cloudflare**. لكنها تترك حدود العقود والواجهات والقرارات واضحة كي تأتي تلك الحزم لاحقًا دون إعادة كتابة تطبيق العميل.

## تعريف Customer App GO

لا يصدر قرار GO إلا عند تحقق البنود التالية معًا: إقلاع Web وAPK دون MaterialLocalizations أو Runtime errors، RTL والهوية والأصول الصحيحة، Demo journey كاملة، Auth/Guest behavior سليم، البحث والفلاتر والمنتج والمتجر والفواصل الاجتماعية والطلبات والمراسلة والإشعارات تعمل، Repository boundaries قابلة للتبديل، اختبارات Unit/Widget/Journey تمر، Web responsive، APK مثبت ويعمل على محاكي المستخدم، ووجود مصفوفة traceability مرتبطة بالملفات والاختبارات والأدلة.
