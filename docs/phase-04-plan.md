# Phase 4 — العقود والنماذج وقاعدة Supabase

## الهدف

تصميم نماذج المجال والعقود النوعية ومخطط Supabase الإنتاجي من الصفر، مع الحفاظ على Demo-First وعدم جعل قاعدة البيانات أو RLS أو API تقود UX أو Domain Model قبل استقرار العقود.

## المخرجات

سيتم إنشاء عقود Dart لتطبيق Flutter، وعقود TypeScript لمشاريع Web عند الحاجة، مع تطابق دلالي. سيُكتب مخطط SQL ومigrations وRLS وفهارس وسياسات ملكية وأدوار، ثم يُطبق على مشروع Supabase الإنتاجي المعتمد بعد التحقق من المشروع المستهدف. سيُحفظ كل ذلك في `database/` و`packages/contracts_*` مع سجل قرارات.

## حدود البيانات

يشمل المخطط المستخدمين والملفات الشخصية والتجار والمتاجر والمنتجات والصور والتصنيفات والتصنيفات المرجعية والمناطق والشهادات والتقييمات والتعليقات والإعجابات والمفضلة والمتابعة والطلبات وطلبـات التواصل والرسائل والإشعارات والبنرات وطرق الاستلام والتوصيل وروابط التواصل والمعرض والإحصاءات وأدوار الإدارة وسجلات التدقيق. لا تُضاف جداول لا تخدم Product Model المعتمد.

## ضوابط التنفيذ

Supabase هو مصدر الإنتاج الرسمي للبيانات والمصادقة والتخزين، لكنه لا يُستخدم كشرط لتشغيل Demo Mode. سيُتحقق من SQL والعقود برمجيًا، وتُختبر سياسات RLS، ولا يُعتبر إنشاء Schema أو migrations أو RLS دليل اكتمال Feature.

## بوابة المرحلة

تتبع المرحلة: `PLAN → IMPLEMENT → RUN → VERIFY → TEST → VISUAL CHECK → ARCHITECTURE CHECK → FIX → RETEST → EVIDENCE → GIT COMMIT → ACCEPTANCE GATE`. لا يبدأ ربط التطبيق أو الواجهات بمصدر الإنتاج قبل إتمام هذه المرحلة والمرحلة الخاصة بـ Demo Data Layer.
